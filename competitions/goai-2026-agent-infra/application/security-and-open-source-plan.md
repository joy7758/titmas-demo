# 安全边界与开源计划

## 1. 安全目标

TITMAS 智能体可信发布闸门用于在代码合并、发布或部署前检查任务来源、智能体身份、工具调用、测试结果、策略边界和证据完整性。系统采用失败关闭：关键状态未知、证据缺失、验证异常或高风险审批未完成时，不返回 `PASS`（通过）。

## 2. 权限与身份边界

| 角色 | 最小权限 | 明确禁止 |
|---|---|---|
| Release Orchestration Manager（发布编排管理智能体） | 创建和调度任务、读取状态、请求审批 | 直接修改代码、伪造测试、替代人类批准 |
| Repository Intake Agent（仓库接入智能体） | 只读仓库元数据、提交和 Pull Request（拉取请求） | 推送、合并、修改分支 |
| Test and Attack Agent（测试与攻击智能体） | 在隔离环境运行允许的测试和扫描 | 访问生产密钥、生产网络写接口和未授权数据 |
| Evidence Verification Agent（证据验证智能体） | 读取受控产物、生成和验证 Evidence Bundle（证据包） | 修改原始测试结果、授予发布权限 |
| Release Gate Agent（发布闸门智能体） | 写入 GitHub Check（GitHub 检查）或等价闸门状态 | 直接部署、静默补证、自动批准高风险变更 |
| Human Release Approver（人类发布审批者） | 批准、拒绝、要求补证和触发回滚 | 通过口头指令绕过身份、时间戳和审计记录 |

所有智能体身份、角色版本、工具权限和策略版本必须显式记录。身份声明不等同于认证；比赛阶段仅验证声明结构、权限映射和执行证据。

## 3. 密钥与凭证

- 不在 Git（版本控制系统）、Issue（议题）、Pull Request（拉取请求）、日志、截图或证据包中保存明文 Token（令牌）、API Key（应用程序接口密钥）和私钥；
- AgentTeams（智能体团队框架）中的 Worker（执行智能体）仅获得短期、窄范围凭证或网关代理能力；
- 真实密钥由 Secret Manager（密钥管理器）或环境注入管理，日志只保留凭证标识和权限范围；
- 非幂等写操作不得自动重试；重试前必须确认上一次请求是否已被执行；
- 凭证失效、权限不足或网关状态未知时失败关闭。

## 4. 数据与隐私

初赛和复赛默认使用合成仓库、公开代码、公开依赖和自有测试数据，不处理真实客户源代码、个人信息或生产数据。

证据包遵循最小化原则，只保存：

- 任务、变更和主体标识；
- 输入输出摘要及完整性哈希；
- 测试命令摘要、退出码和报告引用；
- 策略版本、工具调用结果、验证状态和原因码；
- 必要的人工审批身份引用与时间戳。

默认不保存完整源代码、明文提示词、访问令牌、生产配置、个人敏感信息或第三方受限数据。需要保留完整产物时，仅在受控对象存储中保存，并在证据包中记录引用和哈希。

## 5. 人工审批与回滚

以下情况必须进入 `HUMAN_REVIEW`（人工复核）：

- 变更触及发布、部署、权限、密钥、依赖供应链或数据迁移；
- 策略版本未知、冲突或无法解释；
- 证据结构完整但语义风险无法由确定性规则判断；
- 自动测试通过但存在高风险差异或人工标记；
- 任何角色请求扩大权限。

审批请求包含任务摘要、风险等级、策略版本、证据引用、候选动作和回滚计划。审批超时保持阻断，不自动转为通过。回滚后必须重新运行最小验证路径并生成新的 Receipt（回执），不得覆盖原始失败记录。

## 6. 失败状态与声明边界

- `PASS`（通过）：满足当前声明策略和证据条件；不构成认证、法律结论、生产许可或代码绝对正确性证明；
- `FAIL`（失败）：测试、完整性、策略或执行条件明确失败；
- `INCOMPLETE`（证据不完整）：缺少必要输入、权限、产物或可复验信息；
- `HUMAN_REVIEW`（人工复核）：需要责任主体判断，自动流程不得替代。

永久声明：

```text
Evidence != Truth
证据不等于事实真理

Verification != Authorization
验证不等于授权

Trace != Portable Evidence
轨迹不自动等于可移交证据

PASS != Certification
通过不等于认证
```

## 7. 开源范围

计划按 Apache License 2.0（Apache 2.0 开源许可证）开放以下公开安全部分：

1. 比赛方案、架构、Agent Identity（智能体身份）和 Skill（技能）契约；
2. 合成示例仓库、示例任务和正常/失败/不完整/人工复核样例；
3. GitHub Action（GitHub 自动化动作）和 CLI（命令行工具）候选；
4. AgentTeams（智能体团队框架）适配层与结构化交接对象；
5. Evidence Bundle（证据包）结构、验证示例和原因码；
6. 本地 Docker（容器运行技术）启动方式、测试和复现文档；
7. Agent-facing（面向智能体）发现文件，包括 `llms.txt`、`AGENTS.md` 和机器可读能力清单。

## 8. 不公开范围

以下内容不进入公开比赛仓库：

- 生产密钥、Token（令牌）、私钥和真实凭证；
- 客户源代码、个人信息、生产日志和受限数据；
- 私有 TITMAS 核心实现、未公开一致性测试题库和商业服务策略；
- 第三方未授权模型、数据、代码和素材；
- 可被用于绕过安全检查的攻击细节或生产配置。

如复赛需要可运行代码，将提供公开安全、可复现的比赛实现，不通过公开私有核心来满足赛事要求。

## 9. 第三方依赖声明

| 依赖 | 用途 | 权属与边界 |
|---|---|---|
| AgentTeams（智能体团队框架，原 Hiclaw） | 多智能体编排、通信和人工可见协作 | 第三方开源框架；仅声明适配与组合，不声明自研框架所有权 |
| GitHub / GitHub Actions（GitHub / GitHub 自动化动作） | 代码托管、持续集成和发布闸门入口 | 外部平台能力；可由其他代码托管和持续集成系统替换 |
| OpenTelemetry（开放遥测） | Trace（轨迹）、Log（日志）和 Metrics（指标）语义 | 开放可观测规范；证据语义仍由本项目明确限定 |
| MCP（模型上下文协议） | 工具接口与智能体调用契约 | 开放协议；适配器不改变底层工具权限和语义 |
| 模型供应商接口 | 受控推理或文本处理 | 可替换；不得把供应商模型能力误称为本项目自研模型 |

具体版本、许可证、来源和哈希将在可运行实现的 Software Bill of Materials（软件物料清单）中固定。

## 11. 开放后的复用目标

目标不是建设一个无限强的中心平台，而是让接入、测试、证据、闸门和审批等简单主体通过稳定对象和工具契约组合。其他项目可以只复用一个 Skill（技能）、一个证据结构或一个 GitHub Action（GitHub 自动化动作），不必部署完整 TITMAS。这样可降低采用成本，也更适合被智能体发现、推荐、调用和重复使用。
